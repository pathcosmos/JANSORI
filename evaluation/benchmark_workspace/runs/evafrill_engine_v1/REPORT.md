# EVAFRILL-Mo 증분 디코딩 엔진 검증·성능 (Goal 1-B) — 2026-11-18

## 결론
- **최종 엔진(배치 불변, `EvafrillEngine(batch_invariant=True)` 기본값)은 3개 체크포인트(pretrain, sft-v2, slerp) 모두 V1~V4를 통과한다** (이 폴더의 `verification.json`, `verification_V3bc.json`, `verification_final.json`, `perf.csv`가 최종 엔진 결과다. 실행 로그와 원본 기록은 `v2_batch_invariant/`, 이전 엔진 결과는 `v1_batch_variant/`).
  - V1 prefill: 원본 전체 forward와 비트 단위로 같다 (12/12).
  - V2 decode 256단계: FP32 기준선 대비 오차가 원본 BF16과 같은 수준이다 (12/12).
  - V3: 사용자가 승인한 변경 기준(교사 강제 결정 일치 + 자유 생성 분기는 원본 margin <0.5에서만)으로 3/3 통과한다. 사전 등록 기준(6/8 이상 동일)으로는 slerp만 통과(6/8)하고, pretrain 1/8, sft-v2 5/8이다(아래 경위).
  - V4: Goal 문구 그대로("배치 8·32 결과가 배치 1과 동일") 측정 전에 등록한 엄격 기준으로 통과한다. 모든 시퀀스의 토큰열이 같고, 매 단계 로짓도 비트 단위로 같다 (6/6).
  - CUDA graph와 eager는 비트 단위로 같다.
- **속도** (`perf.csv`): 원본 생성(매 단계 전체 재계산) 대비 배치 불변 모드(용량 32) 4.0~80배, 크기 맞춤 모드 5~105배.
  - 단일 스트림: 원본 약 34 tok/s → 배치 불변 약 165 tok/s / 크기 맞춤 약 275 tok/s
  - 입력 3968·배치 32: 원본은 메모리 부족(45 GiB 할당 실패), 엔진은 13.7 GiB로 3,249 tok/s(출력 512)
  - 배치 불변 모드는 결과가 배치 구성과 무관하게 재현된다. 대신 소배치 decode가 약 40% 느리다(행 32개·길이 4608로 고정 실행). 평가에는 배치 불변 모드를 쓰고, 속도만 중요하면 `batch_invariant=False`를 쓴다.

## Goal 1 완료 판정
- 사용자 결정(2026-11-18): **승인된 V3 변경 기준으로 Goal 1 완료 처리.** Goal 원래 문구의 V3(greedy 6/8 동일)는 불충족(pretrain 1/8, sft-v2 5/8, slerp 6/8)이었음을 여기에 남긴다.
- 그 밖의 기준은 원래 문구대로 충족했다: V1·V2 사전 등록 기준, V4 "배치 8·32 = 배치 1"(토큰·로짓 비트 동일), 성능 수치, 테스트 554개(GPU·llama.cpp·자체 기동 Ollama 포함).

## 검증 경위 (실패 기록과 기준 변경)
1. **엔진 v1** (배치마다 형태가 바뀌는 decode; 결과는 `v1_batch_variant/`에 보존):
   - V1·V2 통과, V3 불통과(2/8, 5/8, 2/8)
   - V4는 처음 등록한 기준(분기는 근접 동률에서만 허용)으로만 통과했다(동일 6/8, 12/32, 7/8, 15/32). Goal 문구("동일")를 충족하지 못했다.
2. **V3 원인**:
   - 분기는 모두 원본 margin 0.0~0.125의 bf16 동률이었다.
   - 원본 자신도 같은 위치 로짓이 입력 길이에 따라 최대 0.28 달라진다(`prefix_consistency_probe.log`). 그래서 캐시를 쓰는 엔진은 원본의 길이 의존 동률 깨기를 원리적으로 재현할 수 없다.
   - 대조군 V3c: 원본 BF16 대 FP32 greedy 동일 0/8, 3/8, 6/8
   - **사용자 승인으로 V3 기준을 변경**했다(`tolerance_amendment_v3.json`). 원래 기준 파일과 결과는 그대로 두었다.
3. **V4 해결**: decode 연산이 모두 행 독립(GEMM 행, selective_state_update/causal_conv1d_update, 배치 어텐션)이라는 점을 이용했다. 실행 형태를 (max_batch 행, max_len 어텐션)으로 고정하는 배치 불변 모드를 만들고, Goal 문구 그대로의 엄격 기준(`tolerance_v4_strict.json`)을 측정 전에 등록한 뒤, 전체 검증(V1~V4 + V3b/V3c)과 성능 측정을 새 run(`v2_batch_invariant/`)으로 다시 했다. 그 결과를 이 폴더 최상위 파일로 올렸다.
4. 그 밖의 실패 기록:
   - `verify_attempt1_te_keys_failed.log`: pretrain 체크포인트의 TransformerEngine 키. 원본 `_convert_te_state_dict`로 해결했다.
   - 첫 구현의 RoPE fp32 표 문제: prefill 최대 차 0.64였고, 원본의 bf16 캐시 표 규칙으로 고쳤다.

## 엔진 구조 (`ko-llm-bench-suite/kobench/standard/evafrill_engine.py`, 원본 소스 수정 없음)
- **prefill**: 원본 블록 연산을 같은 커널·같은 순서로 수행하고(mamba_chunk_scan_combined, causal_conv1d_fn, 원본 apply_rotary_emb·_standard_attention), 마지막 SSM 상태(fp32), conv 입력 마지막 3개, RoPE 적용된 K/V를 꺼낸다. 시퀀스마다 따로 한다(패딩 없음 → 원본과 비트 동일).
- **decode**: causal_conv1d_update, selective_state_update(z, D, dt_bias, dt_softplus; mamba_ssm Mamba2.step과 같은 확장), KV 캐시 어텐션(원본과 같은 bf16 matmul → fp32 softmax → bf16). 시퀀스별 위치·길이가 독립이다.
  - 배치 불변 모드(기본): 행 수 max_batch·어텐션 길이 max_len으로 고정하고 빈 행은 더미로 채운다. 그래서 같은 프롬프트의 결과는 함께 들어간 다른 프롬프트 수와 무관하게 비트 단위로 같다.
  - decode 단계는 CUDA graph로 캡처한다.
- **RoPE**: 원본 규칙을 따른다. 길이 ≤4096이면 `model.to(bf16)`으로 bf16이 된 캐시 표, 초과면 fp32 표다.
- **lm-eval**: `EvafrillLM.generate_until`(gen_kwargs별 묶음, until, EOS, max_gen_toks, do_sample이면 temperature/top_p + seed; 기본 `gen_batch_size`=32 용량 배치 불변), `apply_chat_template`(formats.yaml 학습 형식).

## 한계
1. **배치 TTFT**: 시퀀스마다 따로 prefill하므로 배치가 크면 첫 토큰이 늦다(128토큰·배치 32: 원본 0.06초 vs 엔진 0.97초). 묶음 prefill은 원본과의 비트 동일을 깰 수 있어 하지 않았다.
2. **배치 불변 모드의 소배치 비용**: 행 32·길이 4608 고정이라 단일 스트림이 약 40% 느리다(165 vs 275 tok/s).
3. **4096 초과 구간**: 원본은 전체 길이가 4096을 넘으면 앞쪽 K까지 fp32 RoPE로 다시 계산하지만, 캐시는 다시 계산할 수 없다. V2 L=4000(4257 위치까지)은 기준 안이었다.
4. **개행 `<unk>`**: 토크나이저가 개행·탭을 `<unk>`(3)로 인코딩하고, decode할 때 이 토큰은 사라진다. 생성 결과의 처리는 Goal 2의 dev 결정 사항이다.
5. 자유 생성은 bf16 동률 지점에서 원본과 갈릴 수 있다(V3). 같은 이력에서의 결정은 원본과 같다(V3b).
