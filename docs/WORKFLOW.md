### F0~F1: 실행 가능한 감사 준비와 전체 감사

적용 예정: scripts/validate_source_manifest.py, data/quality_report.py, scripts/check_data_readiness.py, common/data_contracts.py, 필요한 별도 source finalization helper와 tests. 기존 API/진행 증거를 보존하며 새 동작을 검증한다.

2. 파일별 시작/완료/오류/행수·읽은 byte·시간·SHA를 원자적으로 저장한다. 동일 계약의 완료 파일만 재사용하고, 증명 없는 partial·내용/정책 변경은 거부 또는 별도 출력으로 처리한다. 한 파일 중간에서 실패하면 그 파일부터 다시 읽는 것을 초기 재개 단위로 삼는다.
3. 웹은 text와 이후 사용 field, 코드는 repo_name/path/license/language/source_row/content_sha256 등 실제 소비 필드를 decode한다. non-string/null/빈 repo/행 범위·저장 body SHA 불일치를 거부한다. 파일 SHA만 새로 산출했다고 기존 내용과 같다고 보증하지 않으며 감사 시점의 고정 증명을 남긴다.
4. 각 source의 파일1개, 총6파일로 pilot을 실행한다. compressed/uncompressed 읽기·rows/s·CPU/RSS·SHA 비용을 측정하고 전체231GiB 대상의 예상 시간을 범위로 갱신한다. 현재 감사기는 text 읽기와 파일 hash가 별도 pass이므로 전체 읽기량은 입력 크기보다 커질 수 있다.
5. worker1에서 시작하고 여유가 확인되면 최대2로 올린다. 첫 실제 job의 메모리 budget은16GiB, 디스크 여유 최소200GiB를 유지하는 계획으로 두고 파일럿 측정에 맞춰 설정한다. 큰 scan 두 개를 동시에 실행하지 않는다.
6. 내용 inventory ID에는 source별 실제 file SHA/행수/정책/출처를 넣고, 문서 상태 metadata와 구분한다. candidate 감사→검토→ready의 연결 증명을 만들고 source 소비자가 고정 file SHA와 다른 입력을 거부하는지 검사한다. split/tokenizer는 최종 ready manifest ID와 내용 ID를 함께 기록한다.
7. 최종726파일의 감사 행수/receipt 합계가 일치해야 content_audit를 통과시킨다. 손상 파일은 source/file/row group과 원인을 남기고 해당 source만 대기시킨다. 복구가 필요하면 별도 결과를 만들어 검증하고 원자료 덮어쓰기는 기존 확인 규칙을 따른다.

### F2~F3: 품질 판단과 최종 source 고정

- 웹 유사중복: FW2↔HPLT를 우선하고 영어를 포함한 source/file/row-group/문서 길이 strata에서 고정 표본을 확대한다. 최초 목표 source당2,000문서, 저장 본문128MiB 이내·읽기/비교량/시간 상한을 별도로 정한다. 원래256표본보다 넓은 범위를 만들되 대표성/후보 재현율을 보장한다고 주장하지 않는다.
- 후보 생성 검증: 합성 변형 쌍에 더해 작은 고정 하위 표본의 완전 비교와 대조해 관측된 탐지 누락을 측정한다. Jaccard threshold0.8/0.9/0.95 등의 진단값은 실행 전에 정한다. 특정 threshold의 무일치를 전체 무중복으로 쓰지 않는다.
- 코드↔웹: 이미 완료한 코드 내부 exact/코드↔수학 범위는 재사용한다. **선택한 전체 코드 파일 hash와 웹 전문 raw exact의 교차**를 다음 우선 범위로 삼고, 필요한 지문을 F1 읽기에서 함께 수집하는 구현을 먼저 검증한다. fenced block/inline/일부 조각/변형 코드 검사 범위는 별도 지표로 결정한다. 문서에 코드 일부가 일치한다고 문서 전체를 자동 삭제하지 않는다.
- 코드 블록 표본: 무작위 표본에 fence가 없었다는 이유로 통과시키지 않는다. fence가 실제로 있는 별도 frame을 확보할지/전체 stream에서 block 지문을 수집할지 비용을 측정한 후 결정하고 미검사 범위를 적는다.
- 공식 benchmark는 사용자 별도 작업이다. F2에서 평가 원본 schema/revision/license/split과 오염검사 범위를 결정할 시점임을 먼저 알린다. 원본 미확보/범위 미확정이면 해당 조건은 pending으로 유지한다. 다운로드·adapter·채점은 이번 병행 범위에서 실행하지 않는다. F7 진입 전 별도 준비 시점을 다시 안내한다.
- 조치 결정: 추가 제거/비중 조정/현 데이터 유지 중 근거 있는 선택을 기록한다. 사전학습 학습 목적에 맞는 범위 결정을 할 수 있지만 미검사 범위와 신뢰 한계를 남긴다. 검사 범위 밖의 품질까지 통과로 바꾸지 않는다.
- split 정책 초안: seed1234·eval fraction0.01을 출발 후보로 삼되 아직 확정값으로 표시하지 않는다. 웹 exact/NFC와 코드 repo 연결 component, 한/영 holdout token 목표를 고려해 정책을 확정하고 실제 F4/F6에서 분포/유효 토큰 수를 다시 확인한다.

### F4: 전체 그룹 분리의 확장/용량 검증

현재 근거는 synthetic10만 건 build116.76초/verify12.91초/DB81,776,640 bytes다. 이를1.29억 문서의 소요시간이나 용량으로 선형 외삽해 실행 완료를 약속하지 않는다.

- 먼저 합성100만 문서 case를 하나 실행하고 필요하면300만으로 확대한다. 반복 repo·소스 간 exact·NFC 연결·긴 component·빈/평가 전용 shard를 포함한다. fixture는 실제 final ready 데이터와 구분한다.
- SQLite cache/index·batch commit·finalize transaction의 시간/임시 journal 크기·최대 RSS/DB byte를 측정한다. 필요 시 새 split 출력의 설정을 보완하며 기존 exact_v1 index는 변경하지 않는다.
- 단계별 시간 제한/진행 checkpoint를 두고 ingest/assign/finalize/publish의 중단 재개를 확인한다. 단일 finalize transaction이 커서 운영 가능 범위를 넘으면 실제 전체 실행 전에 분할 적용/재개 방식으로 보완한다.

### 단계 2 — 전처리 보완과 데이터 품질 확정

REF-DATA / D03: 코드 의미 보존·소스 간 dedup·holdout 분리의 검증은 위 실행 완료 조건을 함께 따른다.

**전환 알림: GPT-6.1 Sol / High. 필터·중복제거 로직 검증이 필요하다.**

작업:
1. clean.py의 샤드 전체 메모리 적재를 점검하고 row-group/batch 단위 출력과 재시작 처리를 개선한다. 토큰화 스크립트의 전체 샤드 적재 문제도 단계 4 전에 개선한다.
2. 대표 샤드 1~2개로 최대 RSS와 처리량을 측정한다. CPU 수만 보고 워커를 정하지 않는다. 초기 4~8 workers에서 시작해 메모리 여유와 I/O를 보며 확대한다.
3. 한국어·영어·수학별 필터 제거율과 통과/탈락 샘플을 확인한다. OWM의 수식이 low_alnum 필터 때문에 과도하게 제거되지 않도록 별도 정책을 구현한다.
4. HPLT `u`와 FW2 `url`의 정규화 규칙 및 양방향 교집합률을 기록한다. URL 중복률을 텍스트 중복률과 동일시하지 않는다.
5. 샤드 내부뿐 아니라 소스·샤드 사이 정확중복 제거를 구현한다. 현재 `h`는 마스킹 전 문자열의 해시이므로 최종 텍스트 중복도 확인한다. 필요하면 내용 비교를 통해 해시 충돌을 처리한다.
6. 대표 표본에서 유사중복을 측정하고 MinHash 적용 또는 HPLT 비중 축소 여부와 근거를 기록한다. 원본을 덮어쓰지 않고 파생 산출물 경로를 사용한다.
7. 코드 소스 접근 가능 여부·이용 조건·언어 구성·규모를 조사한다. 확보하지 못했으면 코드 10%를 포함한 최종 데이터 믹스를 완료로 표시하지 않는다.
8. 평가에 사용할 문서가 다른 소스의 중복 문서로 학습에 남지 않도록 분리·중복제거 순서를 정한다.

검증: 중복 문서가 다른 샤드/소스에 있는 사례, 정상 수학 문서, 한국어/영어 혼합 문서, 마스킹 후 동일해지는 문서, 중단 후 재시작을 확인한다. 중요한 변환 로직에 한해 작은 의미 있는 테스트를 작성한다.

완료 조건: 소스별 입력/유지/제거 문서·문자 수, 제거 사유, 중복률, 샘플 검토 결과, 처리 코드 버전이 기록됨. 새 정제본 경로가 확정됨.

### 단계 3 — 최종 토크나이저 학습·검증

REF-TOK: 검증된 dedup 입력 경로·최종 소스 구성·산출물 식별 조건을 먼저 확인한다.

**권장: GPT-6.1 Sol / High 유지.**

작업:
1. 목표 학습 언어와 코드·수학을 포함한 byte 기준 표본을 확정한다. 현재 스크립트는 없는 소스를 제외하고 재정규화하므로, 소스 누락 상태로 최종 학습하지 않도록 검사한다.
2. 초기 총 표본 3000MB를 기준으로 언어별 실제 투입량을 기록한다. 코드 소스를 추가했다면 현재 MIX에도 반영한다.
3. 별도 후보 파일로 학습하고 vocab 65536, 특수토큰 ID, EOS/PAD, 숫자 분리, Unicode 처리를 검사한다.
4. 한국어 chars/token 약 2.3은 참고 목표로 삼되 영어·코드·수학 효율도 함께 본다.
5. roundtrip은 NFC 정규화 결과와 비교한다. 정규화에 의한 의도된 차이와 실제 복원 오류를 구별한다. 특수토큰 문자열이 본문에 나타나는 사례도 검사한다.
6. 통과한 tokenizer의 해시·표본 구성·코드 버전을 고정한다. 이후 변경하면 관련 토큰 데이터를 새로 생성해야 한다.

완료 조건: 최종 tokenizer.json과 해시, 언어별 효율, 정규화 기준의 복원 오류 0, 특수토큰 검증 결과가 존재함.

### 단계 4 — 토큰화·holdout·mix 생성

REF-TOK / T01,T02 및 REF-DATA: cast 이전 범위 검사·캐시 버전·중복제거 후 분리를 완료 조건에 포함한다.

**권장: GPT-6.1 Sol / High 유지.**

작업:
1. 문서 단위 holdout을 정하고 학습 문서와 분리한다. 한/영 각 약 50M tokens 목표는 실제 토큰 수로 맞춘다. 50,000문서가 50M tokens와 같다고 가정하지 않는다.
2. `.bin`은 uint16이므로 모든 token ID가 0~65535에 들어가는지 검사한다. EOS·문서 경계·빈 문서 정책을 고정한다.
3. 스트리밍으로 토큰화하고 임시 파일→완성 파일→`.done` 순서로 확정한다. holdout도 중단·재시작 시 일관되게 생성한다.
4. `.done` 존재뿐 아니라 파일 길이·토큰 수·tokenizer 해시·입력 버전을 검증한다. 설정이 바뀌었을 때 오래된 결과를 조용히 재사용하지 않는다.
5. 최종 mix의 소스별 실제 고유 토큰량과 sampling weight를 확인한다. 예상 반복 노출량은 `총 학습 토큰 × 소스 비중 / 소스 토큰량`으로 기록한다. 현재 샘플러는 복원추출이므로 이는 엄밀한 전체 데이터 순회 epoch가 아니다.
6. 빈 소스, 음수/0 가중치, seq_len+1보다 짧은 샤드, 잘못된 경로, 토큰 수 불일치를 검출한다.
7. 한국어 위키처럼 작은 소스가 과도하게 반복되지 않도록 실제 양을 보고 비율을 조정한다.

완료 조건: 검증된 토큰 파일, 분리된 한/영 holdout, 상대경로 mix.json, 소스별 토큰·비중·반복 노출량 표가 존재함.

### 단계 5 — 모델·학습 루프 검토 및 8GPU 스모크

REF-TRAIN 및 REF-DATA / D01,D02: 실제 데이터 검증 전에 sampler 경계·버전 조건을 통과한다.

**전환 알림: GPT-6 Astra / High. 단계 0 뒤 선행 가능.**

작업:
1. attention/GQA/RoPE, causal mask, loss의 label shift, 파라미터 수, bf16, weight tying과 초기화를 점검한다.
2. FSDP2 초기화·gradient accumulation·gradient synchronization·gradient clipping·optimizer state를 검토한다.
3. 가짜 데이터로 8랭크의 학습·평가·저장·종료를 실행한다. 학습은 유한 loss에서 시작하고 구조화된 데이터에 대해 감소 경향을 확인한다. 매 step 단조 감소는 요구하지 않는다.
4. holdout window 수가 world size로 나누어떨어지지 않는 조건을 시험한다. FSDP forward 집단통신과 랭크별 평가 횟수 불일치로 hang이 발생하지 않는지 검증한다.
5. 체크포인트 저장, `.complete` 이전 중단, 완전한 최신 체크포인트 선택, 재개 step 및 optimizer state 복원을 확인한다.
6. 짧은 연속 실행과 중간 저장·재개 실행을 동일 설정에서 비교한다. sampler batch는 정확히 일치해야 하며 가중치/loss 차이는 수치 비결정성을 고려한 허용 오차와 함께 기록한다.
7. 비유한 loss/gradient 발생 시 모든 랭크가 안전하게 종료하고 잘못된 체크포인트를 정상 결과로 남기지 않는지 확인한다.

완료 조건: 8GPU 기본 스모크와 평가·저장·재개 검증 로그가 있음. 1GPU 성공 기록을 8GPU 성공으로 대체하지 않음.

### 단계 6 — compile·처리량·메모리 튜닝

**전환 알림: GPT-6 Astra / Extra High (`xhigh`).**

작업:
1. tiny → 1B → 3B 순으로 짧은 성능 측정을 진행한다. tuning 실행은 별도 out_dir를 사용한다.
2. compile off/on, micro batch, accumulation을 비교한다. 실제 tokens/step과 목표 global batch가 일치하는지 기록한다.
3. compile 최초 비용과 warmup을 제외한 안정 구간의 tokens/s, GPU 메모리, step 시간, 평가·체크포인트 비용을 측정한다.
4. 현재 MFU 계산의 하드코딩된 peak와 FLOPs 추정을 점검한다. 추정값을 절대적인 하드웨어 효율로 보고하지 않는다. MFU 35%는 목표이며 미달이면 실제 tokens/s로 일정부터 다시 산출한다.
5. 남은 토큰 수 / 실제 tokens/s에 평가·저장 시간을 더해 본학습 소요 시간을 추정한다. 고정된 10일 완료를 보장하지 않는다.
6. 실제 mix를 사용한 짧은 검증으로 I/O 병목과 안정성을 재확인한다.

완료 조건: 검증된 1B/3B 설정, 성능 비교표, 메모리 여유, 학습 기간·체크포인트 공간 추정이 존재함.

### 단계 7 — 최소 평가 준비와 1B 리허설

REF-EVAL / E01~E03은 리허설 시작 전 필수. HF 변환 평가를 사용할 경우 REF-EXPORT / X01도 선행한다.

**전환 알림: GPT-6 Astra / High.**

작업:
1. 한/영 holdout loss를 분리 보고하고 perplexity 계산, 고정 생성 프롬프트·seed·길이·샘플링 설정을 준비한다.
2. KMMLU/KoBEST/HAE-RAE 등 최종 벤치마크의 평가 입력과 점수 계산을 준비한다. 데이터 접근과 이용 조건은 확보 시 확인한다.
3. 1B를 짧게 돌려 수치·로그·평가·체크포인트를 점검한 후 약 10B tokens 리허설을 수행한다.
4. 재개, loss·gradient norm·언어별 holdout 곡선, 속도·저장 시간, 반복 데이터 영향을 확인한다.
5. 리허설 결과로 설정을 검토한다. 1B에 적합한 LR을 3B에 검증 없이 그대로 적용하지 않는다.

완료 조건: 리허설 실제 학습 토큰 수와 결과, 재개 증거, 고정 평가/생성 결과, 3B에 반영할 설정과 미해결 사항이 기록됨.

### 단계 8 — 3B 본학습 사전 검토

사전학습에 적용되는 REF-DATA/TOK/TRAIN/EVAL 및 해당 시 EXPORT의 결과·미해결 사항을 대조한다.

**전환 알림: GPT-6 Astra / Extra High (`xhigh`).**

검토 항목:
- 데이터 revision·정제 버전·최종 tokenizer 해시·mix·holdout 분리·실제 토큰량.
- 3B 구조, 실제 global batch, LR/WSD/max_steps, compile, 안정성.
- 8GPU 평가·체크포인트 재개 결과, 디스크 여유, 로그·보존 정책.
- 예상 GPU 실행 시간, 목표 tokens, 중단·재개 명령, 운영 중 관찰할 지표.
- 미해결 문제가 본학습을 막는지와 근거.

완료 조건: 실행할 정확한 config와 명령, 예상 시간·공간, 검증 결과를 제시하고 사용자에게 본학습 시작 확인을 받음. 이는 CLAUDE.md의 기존 요구이며 모델 변경 알림과는 별개다. 확인 전까지 준비·검토는 완료한다.

### 단계 9 — 3B 본학습·모니터링

**전환 알림: GPT-6.1 Sol / Medium.**

작업:
1. 승인된 설정으로 실행하고 최초 로그·loss·GPU 메모리·속도를 즉시 확인한다.
2. 학습 중 loss, gnorm, LR, tokens/s, 한/영 holdout, 체크포인트 완성 여부, 디스크·OOM 이벤트를 추적한다.
3. 시작·재개·설정 변경 직후에는 수분 단위로 확인한다. 활성 작업 중 진행 상황은 최소 60초 이내 간격으로 알리되 같은 내용을 반복하지 않는다.
4. 장시간 무인 감시나 대화 종료 후 알림은 별도 프로세스·서비스·알림 채널이 실제로 구축됐을 때만 약속한다. 현재 문서 지침만으로 상시 감시가 생기지 않는다.
5. NaN/Inf, 반복 OOM, 분산 hang, 재개 불일치가 나오면 원인을 분석하고 Astra / xhigh 전환을 권장한다. 결함이 있는 실행은 안전하게 중단하고 완전한 체크포인트를 보존한다.
6. 결과를 조용히 바꾸는 LR/mix/max_steps 조정은 하지 않고 변경 근거와 새로운 실행 버전을 남긴다.

완료 조건: 실제 목표 토큰량 도달, 마지막 완전한 체크포인트, 최종 설정·학습 기록·운영 이슈 정리.

### 단계 10 — 최종 평가·SFT·재현 자료

REF-SFT / S01,S02,T02,E02 및 변환 시 REF-EXPORT를 적용한다. REF-PREF는 별도 도입 판단 후에만 적용한다.

**전환 알림: GPT-6.1 Sol / High. 복잡한 원인 분석은 Astra / High 또는 xhigh.**

작업:
1. base 모델의 한/영 holdout, 한국어 벤치마크, 보조 영어 벤치마크, 고정 생성 샘플을 평가한다.
2. tokenizer/model/config를 함께 로드하는 추론 경로를 검증한다.
3. 한국어 instruction 데이터의 이용 조건·품질·분리·대화 형식을 확인하고 SFT 및 평가를 구현한다.
4. SFT 전후 결과를 비교한다. base 체크포인트는 별도로 보존한다.
5. 학습 명령·버전·데이터 목록·해시·평가 설정·제한 사항을 정리한다. 외부 업로드는 기존 사용자 확인 규칙을 따른다.

완료 조건: 평가 보고서, 재현 가능한 추론·평가·SFT 명령, 검증된 산출물 목록.

## 4. 모델 변경 알림 운영 규칙

### 현재 적용되는 방식

현재는 **단계별 전환 권장 알림** 방식이다. AGENTS.md는 실행 지침이며 모델 선택기를 자동 조작하는 기능이 아니다. 주 대화의 모델/effort를 확인할 수 없으면 현재 선택을 추정하거나 변경 완료라고 말하지 않는다.

알림이 필요한 시점:
1. 새 단계 시작: 단계 번호, 다음 작업, 권장 모델/effort를 한 번 안내한다.
2. 권장값 변경: 변경 이유와 다음 검증 목표를 알린다. 같은 모델에서 effort만 달라도 알린다.
3. 오류로 난이도 상승: 진단 결과와 Astra / xhigh 권장을 안내한다. 단순 일시적 네트워크 오류는 재시도 가능한 범위에서 처리한다.
4. 문제 해결 후: 해당 단계 기본 권장값으로 복귀할 시점을 알린다.
5. 단계 종료: 완료 증거, 미해결 사항, 다음 단계와 다음 권장값을 남긴다.

알림 예시:

> 단계 2 시작: 정제·중복제거 로직을 구현합니다. 모델 전환 권장: GPT-6.1 Sol / High — 소스 간 중복과 수학 필터를 검증해야 합니다.

> 모델 전환 권장: GPT-6 Astra / High — 다음 작업은 8GPU FSDP2 학습·평가·체크포인트 재개 검증입니다.

> 모델 전환 권장: GPT-6 Astra / xhigh — 재개 전후 결과가 허용 오차를 벗어나 optimizer·샘플러 상태를 함께 조사해야 합니다.

> 단계 6 완료: 처리량·메모리·실행 시간을 기록했습니다. 다음은 1B 리허설이며 GPT-6 Astra / High를 권장합니다.

모델 변경은 앱의 모델/effort 선택기 또는 CLI `/model`에서 사용자가 수행한다. 전환 권장은 기술적 실행 필수 조건이 아니다. 모델 변경 응답이 없다고 독립 작업까지 멈추거나 같은 확인을 반복하지 않는다. 실제 변경을 요구하는 명시적 사용자 지시가 있으면 그 경계를 따른다.

### 선택 가능한 자동 위임 방식 — 아직 미적용

사용자가 서브에이전트 위임을 명시적으로 요청하면, 주 대화는 진행·결과 검토를 맡고 단계에 맞는 모델/effort를 지정한 서브에이전트에 범위가 명확한 작업을 맡길 수 있다. 주 대화의 모델 변경과는 다른 방식이다.

- 환경·데이터 점검: Sol / Medium.
- 정제·토크나이저·평가 구현: Sol / High.
- 학습 루프·분산 검토: Astra / High.
- 어려운 분산 오류·본학습 사전 검토: Astra / xhigh.
- 위임 시작 시 작업·모델·effort·대상 파일을 알리고 종료 시 결과와 검증을 보고한다.
- 모델을 새로 지정한 에이전트에는 목표·제약·입력 파일·완료 조건을 명시적으로 전달한다. 전체 대화가 자동으로 전달됐다고 가정하지 않는다.
- 같은 파일을 여러 에이전트가 동시에 수정하지 않도록 범위를 나눈다. 단일 작업에 불필요하게 여러 에이전트를 띄우지 않는다.
- 도구가 실제 모델 지정에 실패하거나 계정에서 사용할 수 없으면 조용히 다른 모델로 대체하지 않고 상황을 보고한다.
- 위임은 추가 토큰을 사용할 수 있다. 모델 전환에 따른 비용 절감을 보장하지 않는다.
- 현재는 계획 작성 요청만 반영했으며 자동 위임을 활성화하거나 서브에이전트를 실행하지 않았다.

공식 참고: [모델과 effort 선택](https://learn.chatgpt.com/docs/models?surface=cli), [서브에이전트 모델 설정](https://learn.chatgpt.com/docs/agent-configuration/subagents), [AGENTS.md 지침](https://learn.chatgpt.com/docs/agent-configuration/agents-md). 모델 조합은 프로젝트에 대한 권장 운영안이며 공식 성능 보장이 아니다.

## 5. 진행 기록과 인계 형식

단계 종료 또는 의미 있는 상태 변경 시 STATUS.md 상단에 다음을 기록한다.

```text
갱신 시각 (UTC):
현재 단계 / 하위 작업:
상태: 미시작 / 진행 중 / 검증 중 / 완료 / 입력 대기
이번에 확인·완료한 것:
검증 근거: 명령, 로그 경로, 주요 수치, 코드/데이터 버전
남은 문제와 필요한 입력:
산출물 경로:
다음 실행 작업:
권장 Codex 모델 / effort:
실제 실행 모델 / effort: 확인된 경우만 기록, 그 외 확인 불가
모델 전환 안내 여부:
실행 중 프로세스·로그·중단/재개 방법: 해당 시
```

가짜 데이터 성공은 실제 데이터 성공과 구분한다. 계획, 코드 구현, 실행 성공, 산출물 무결성 확인을 각각 구분한다. 모델 알림 지침의 존재를 자동 모델 전환 또는 백그라운드 상시 감시 구현 완료로 표시하지 않는다.

## 6. 일정 추정과 바로 다음 작업

기존 20일 일정은 초기 목표로 유지하되 현재 단계의 확정 일정으로 사용하지 않는다. 데이터 복구 경로, 전처리 표본 속도, 3B 실제 tokens/s를 얻은 뒤 재산정한다.

| 데이터 준비 1~4 | 복구 경로 및 대표 샤드 측정 후 | 전송량, 필터/중복제거 비용, 코드 소스, tokenizer 시간 |
